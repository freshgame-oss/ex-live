# 简化技术中文写作规则

本文件改编自 [dualface/ste-zh](https://github.com/dualface/ste-zh)。规则编号沿用该项目的 R1–R25，便于核对；不是 ASD-STE100 标准的规则编号。许可见 [第三方声明](../THIRD-PARTY-NOTICES.md#ste-zh)。

这些规则默认用于所有 ex-live 生成、修补的中文内容。页面正文、标题、图表标签和视频旁白都在范围内。代码、命令、路径、标识符、界面字面量、原样引文保持原文。用户指定的语言、格式与任务范围优先。

## 词

- **R1 一词一义。** 同一概念在全文使用同一个词。不同概念不得为了统一措辞而合并。
- **R2 先定义，后使用。** 专用词在首次出现时解释。术语多时集中定义；通用词不强行解释。
- **R3 用具体动词。** 写「修改配置」，不写「对配置进行修改」。写「检查页面」，不写「做好页面检查工作」。
- **R4 字面量保持原样。** 代码、命令、路径用反引号。引用界面文字时保持拼写和大小写。
- **R5 名词串最多 3 个名词。** 用完整关系拆开连续名词，避免让读者猜修饰对象。

常见改写：

| 原写法 | 改写 |
| --- | --- |
| 对 X 进行修改／检查 | 修改／检查 X |
| 予以 X／加以 X | 直接写动作 |
| 通过 X 的方式 | 用 X |
| 存在 X 问题 | 写出具体现象 |
| 有一定的 X | 写出有来源的数值；没有来源时不编数值 |
| 实现 X 功能 | 写出用户能观察的行为 |

## 句

- **R6 一句一事。** 一句只写一个动作或事实。拆句时保留因果关系、条件和指代。
- **R7 句长上限。** 中文步骤句最多 30 字，描述句最多 40 字。一个汉字计 1 字，一个英文单词、数字或代码标识符计 1 字，标点不计。原样引文与字面量不为凑字数而改写。
- **R8 主动语态。** 写明动作执行者。执行者不明确或不重要时可以保留被动表达。
- **R9 条件在前。** 先写触发条件，再写动作。例：「连接失败时，页面显示错误。」
- **R10 不用双重否定。** 写「必须确认」，不写「不能不确认」。
- **R11 固定情态词。** 表示强制要求用「必须」，表示禁止用「不得」，表示允许用「可以」。不得把能力、依赖或事实预测改成强制要求。
- **R12 主语明确。** 省略主语会产生两种读法时，补出主语。

英文输出沿用步骤句最多 20 个词、描述句最多 25 个词的原则。其他语言遵循用户要求；不能宣称中文规则覆盖其他语言的全部语法。

## 段与结构

- **R13 一段一个主题。** 每段最多 6 句。一个面板回答一个问题。
- **R14 步骤明确。** 操作步骤用编号列表，每步一个动作。动作结果另写一句。
- **R15 并列项清楚。** 三项以上用列表或表格；关系适合画图时使用原有组件。
- **R16 警告先写动作。** 第一句写必须做或不得做的事，第二句写后果。没有实际风险时不增加警告。
- **R17 列举有边界。** 不用「等」「之类」结束清单。列全项目，或给出完整清单的位置。举例时明确写「例如」，不把例子当完整清单。

## 结论、证据与状态

- **R18 结论先行。** 页面导语和交付摘要的第一句回答核心问题。图表不能代替必要的文字结论。
- **R19 状态词固定。** 汇报工作状态时使用下表。普通知识解释不强加任务状态；完成与验证必须分开。
- **R20 如实写验证。** 每项关键结论写明依据与核验范围。没有执行的检查写「未验证」并说明原因。来源文档写了某个结论，只能证明文档有此表述。不得写成亲自运行检查通过。
- **R21 只写读者需要的过程。** 页面与结果摘要不复述工具操作流水账。操作指南本身必须保留步骤；进度说明直接说当前动作。
- **R22 证据可定位。** 来源用可打开的链接，代码证据给文件和行号，检查证据给方法与结果。命令保留完整写法。页面内的本地路径不得伪装成跨设备可访问的链接。
- **R23 决策选项编号。** 用户确实必须作决定时，列编号选项与后果，推荐项放第一。不得为了模板而新增确认步骤。
- **R24 不确定性明确。** 未核实的事实写「未确认」，并说明确认方法。来源表达概率、条件或区间时保留这些限定；不得把来源中的「可能」改成确定结论。
- **R25 不编造。** 事实必须有来源。推断必须标明推断和依据。示例必须注明示例；缺少数据时不得补造数值、验证结果或业务效果。

| 状态词 | 含义 |
| --- | --- |
| 已完成 | 范围内动作全部执行，结果符合要求；不自动表示经过验证 |
| 部分完成 | 只完成部分动作，必须列明未完成项 |
| 未开始 | 没有执行动作 |
| 进行中 | 动作已经开始，尚未结束 |
| 已验证 | 实际检查通过，必须说明方法和范围 |
| 未验证 | 尚未执行检查，必须说明原因 |
| 失败 | 动作或检查不符合要求，必须保留可定位的失败信息 |
| 跳过 | 有意不执行，必须说明原因 |
| 阻塞 | 缺少继续执行的条件，必须说明缺少什么 |
| 未确认 | 事实尚未核实，必须说明确认方法 |

相同证据覆盖多个结论时，可以集中写依据和适用范围。一般解释页用「结论、说明、证据」即可；任务结果页按内容选「改动、验证、未做、待确认」。不得为了凑模板增加空面板。

## 程序检查与 Agent 审阅

每次输出都必须执行两类检查。

1. Agent 审阅全部可见文字：事实、术语、语义、状态、句长和图文一致性。
2. 用原渲染器执行 `lint --style strict`，或让 `render`、`patch`、`video` 以 `--style strict` 检查稿件。

本包的中文程序阈值为步骤句 30 字、描述句 40 字，与 R7 对齐。程序还检查段落句数、部分虚化动词和套话。这些都是启发式检查。

程序不能核验事实、一词一义、全部情态用法或一句一事。当前扫描普通 Markdown 和 callout 正文；图形组件、标题、部分原样内容及行内代码的计数仍依赖 Agent 审阅。零警告不得称为「全部 STE 规则经过程序验证」。

## 交付前自检

- 第一句回答问题，术语全文一致。
- 句子短而完整；条件、主语与指代清楚。
- 标题、表格、图中标签、旁白与正文的表述一致。
- 事实有来源，推断有依据，示例与真实结果分开。
- 未执行的检查没有写成通过。
- 引文、数字、单位、概率与适用范围保持原意。
- 没有通过隐藏文字或关闭检查来消除警告。
- 交付给出产物与实际验证范围。
